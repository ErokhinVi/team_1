# Контракт CIB — кредитный расчёт и предварительное решение

Обновлено 9 октября 2026 года. Новая кредитная часть подготовлена к
разрешённому пользователем выпуску через dev → main. Сверка с договорённостями retail из dev
не завершена: их текст недоступен этой сессии. Ниже — фактический интерфейс
локальной реализации CIB, предлагаемый для соединения с приложением.

## GET /health

Возвращает `status`, `team`, `block`, `commit`, `backend_url`, `products`
и `credit_policy_version`. У новой локальной версии `products=3`,
`credit_policy_version="workshop-credit-v1"`.

## GET /products

Возвращает `{total, items}`. Сохранены `card-debit` и `deposit-base`.
Добавлен продукт:

```json
{
  "id": "consumer_credit",
  "kind": "credit",
  "name": "Кредит наличными",
  "currency": "RUB",
  "rate_pct": 19.9,
  "rate_max_pct": 24.9,
  "min_amount_rub": 30000,
  "max_amount_rub": 3000000,
  "min_term_months": 6,
  "max_term_months": 60,
  "fees_rub": 0,
  "insurance_required": false,
  "decision_scope": "preliminary",
  "policy_version": "workshop-credit-v1"
}
```

## POST /credit/calculate

Расчёт по минимальной ставке 19,9%, **не решение** и не проверка клиента.
Не обращается к блоку данных. Запрос:

```json
{"amount_rub": 100000, "term_months": 12}
```

Ответ: `amount_rub`, `term_months`, `rate_pct`, `monthly_payment_rub`,
`last_payment_rub`, `total_payment_rub`, `overpayment_rub`.
Все денежные поля в ответе — числа в рублях с точностью до копейки.
Последний платёж может отличаться от регулярного из-за округления.
Общая сумма возврата рассчитана по графику, а не простым умножением
регулярного платежа на срок.

## POST /credit/decide

Запрос:

```json
{
  "client_id": "c-01000",
  "amount_rub": 100000,
  "term_months": 12,
  "product": "consumer_credit",
  "purpose": "ремонт"
}
```

Обязательны `client_id`, `amount_rub`, `term_months`. `product` необязателен,
допускает только `consumer_credit`. `purpose` необязателен, до 200 символов;
на решение не влияет. `application_id` сейчас не принимается: этот метод
не работает с сохранённой заявкой.

Сумма: 30 000–3 000 000 ₽, максимум две цифры после запятой; принимается
число или десятичная строка. Срок: целое число 6–60 месяцев. Идентификатор
клиента: до 64 латинских букв, цифр, дефисов и подчёркиваний; первый символ
должен быть буквой или цифрой. Лишние поля отвергаются. Доход, риск,
историю и долг нельзя передать из формы — CIB читает их из блока данных.

Ответ содержит поля расчёта **для запрошенной суммы**, а также:

| Поле | Значение |
|---|---|
| `client_id`, `product` | Клиент и `consumer_credit` |
| `decision` | `approved`, `rejected` или `counteroffer` |
| `status` | Совпадает с `decision` |
| `approved` | `true` только для `approved` |
| `reason_code` | Машинная причина, перечислена ниже |
| `reason` | Понятное объяснение по-русски |
| `counter_offer` | `null` или объект расчёта меньшей суммы на тот же срок |
| `income_rub` | Доход из блока данных |
| `existing_monthly_payment_rub` | Платёж по действующим кредитам из сводки истории |
| `available_monthly_payment_rub` | Бюджет нового платежа после вычета действующих |
| `debt_to_income_ratio` | Доля дохода для запрошенного кредита вместе с действующими; `null` при нулевом доходе |
| `max_debt_to_income_ratio` | `0.4` |
| `decision_scope` | Всегда `preliminary` |
| `can_disburse` | Всегда `false`: ответ сам по себе не разрешает перечисление денег |
| `policy_version` | `workshop-credit-v1` |
| `warnings` | Массив пояснений: предварительность, отсутствие истории, прошлые просрочки |

Причины: `affordable`, `smaller_amount`, `debt_burden`, `risk`,
`overdue_history`, `current_overdue`, `income`, `age`, `product_scope`.

При `counteroffer` основные суммы ответа относятся к исходному запросу.
Новое предложение находится только в `counter_offer`; `approved=false`.
Приложение должно показать новые условия отдельно. Нельзя считать
встречное предложение согласием на исходную сумму или автоматически выдавать его.

## Учебные правила версии v1

Это предложенные нами настройки для мастерской, **не требования ведущего,
не критерии судей и не промышленная кредитная политика**.

- Продукт для физлиц от 18 лет; сегмент `sme` не поддерживается.
- При нулевом доходе нет одобрения.
- При явно переданной текущей просрочке (`summary.has_active_overdue=true`) — отказ.
- При `risk_score >= 0.65` или прошлой просрочке от 60 дней — отказ.
- Ставка 19,9% при риске ниже 0,5, иначе 24,9%.
- Действующие платежи вместе с новым не превышают 40% дохода.
  Учитывается и последний платёж, который может немного отличаться.
- При превышении бюджета предлагается меньшая сумма, округлённая вниз
  до тысяч рублей, на тот же срок. Если даже 30 000 ₽ не помещаются,
  возвращается отказ по долговой нагрузке.
- Отсутствие истории не означает отказ; небольшая прошлая просрочка
  сама по себе также не приводит к отказу.

## Данные от backend: опубликованные обращения

Оба запроса выполняются только на чтение, с ограничением времени ожидания:

- `GET /clients/{client_id}`: обязательны `id`, `age`, `segment`,
  `income_rub`, `risk_score`, `has_overdue_history`.
- `GET /credit-history/{client_id}`: обязательны `client_id`, `total`,
  `active_count`, `active_monthly_payment_rub`, `max_overdue_days`,
  `has_overdue`. Остальные поля, включая `items`, допускаются.
  Если передан `summary.has_active_overdue`, CIB также учитывает его;
  отсутствие этого признака явно отмечается в предупреждениях.

Эти обращения и состав ответа проверены на публичном сервисе данных
9 октября. Клиентские идентификаторы обоих ответов должны совпадать
с запросом. Отсутствующие поля не заменяются нулевым долгом.
Несогласованный размер платежа/количество активных кредитов отклоняется.
Денежные значения должны быть конечными, неотрицательными, до 16 цифр
с максимум двумя после запятой; риск — от 0 до 1 с максимум шестью
цифрами после запятой.

`max_overdue_days` и `has_overdue` описывают прошлую историю. CIB не
объявляет текущую просрочку на основании этих полей; для неё используется
отдельный `summary.has_active_overdue`, если он предоставлен. Значение действующего
платежа используется из сводки backend; его происхождение и полноту
нужно согласовать с владельцем данных для последующей полноценной выдачи.

## Ошибки

- `422` — некорректная сумма, срок, идентификатор, продукт или лишние поля.
- `404` — клиент не найден.
- `503` — данные временно недоступны, неполны или противоречивы. Это
  техническая невозможность рассмотреть заявку, **не кредитный отказ**.

У `404` и `503` возвращается `{detail: "понятное сообщение"}`.
У `422` стандартный массив `detail` с ошибками полей.
Никакие из этих ошибок не создают заявку и не выдают деньги.

## Сохранение, принятие предложения и выдача

CIB не создаёт и не изменяет заявки, не хранит предложения,
не выдаёт деньги и не возвращает подписанного разрешения на выдачу.
Принятие предложения и история заявок относятся к работе retail/backend.
Перед выдачей нужно повторно проверить актуальность условий и долговой
нагрузки на стороне сервера, зафиксировать согласие и защитить выдачу
от повторного нажатия и параллельных запросов.

В опубликованном описании backend указано, что создание заявки со
`status=approved` или перевод существующей заявки в `approved`
сразу выдаёт кредит. **Не отправлять такой статус на этапе простого
просмотра расчёта или предварительного решения.**

## Страница локальной проверки

`GET /` — каталог и форма расчёта/решения для проверки нашего блока.
Адрес: `http://127.0.0.1:8002/`. Это не заменяет клиентский путь в retail.

## Передача контекста коллегам и оставшееся согласование

Перед выпуском сверены метаданные `origin/dev` до `4ef31d8` от 9 октября
(retail-my-credits-spec-v5). В сообщениях
коллег указаны backend contract v3, retail products/spec v4, фильтр текущего
долга, зарплатные признаки и `idempotency_key`. Текст новых соседних
контрактов этой сессии недоступен, поэтому точная совместимость ещё
не подтверждена.

Для соединения нужно уточнить:

- Совпадают ли запрос решения и три исхода выше с тем, что вызывает retail.
  Особенно важны `application_id`, название `counteroffer` и вложенный
  `counter_offer`: это фактический локальный интерфейс, не подтверждённая
  договорённость с retail.
- Нужно ли после обновления backend брать действующий платёж из
  `summary.monthly_debt_payment_rub`, а не из верхнеуровневого
  `active_monthly_payment_rub`, и чем отличаются их периоды расчёта.
- Какие правила предусмотрены для `summary.is_salary_client` и
  `summary.avg_salary_rub`. Эти поля наблюдались в живом ответе, но
  локальная политика CIB их пока не использует.
- Где проверяются согласие клиента, актуальность решения и защита
  повторной выдачи через `idempotency_key`. CIB записи не делает.

Текущий результат: 18 автоматических проверок проходят. Локальный CIB
успешно выдавал все три исхода на данных опубликованного backend.
Сквозной путь retail → принятие предложения → выдача ещё не проверен;
визуальная проверка локальной страницы также не выполнена.

Полный контекст: `cib/CONTEXT.md`. Эта сводка продублирована здесь,
